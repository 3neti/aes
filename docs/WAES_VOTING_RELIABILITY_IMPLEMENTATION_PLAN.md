# WAES Voting Reliability Implementation Plan

## Objective

Prevent overlapping voting and closeout operations, make contention diagnosable, and recover safely from interruptions without duplicating ballots, deposits, or physical prints.

## Baseline

The 2026-11-24 WAES log includes voting-gate lock timeouts and MySQL startup connection errors. The lock holder is unknown. The existing voting gate covers printer calls and closeout as well as voting. File-backed transitions involve multiple writes and are not transactional.

## Delivery

1. Record non-sensitive gate wait and hold durations. Trace every voting gate caller and nested lock, including closeout and printer calls.
2. For the single-host offline appliance, use process-held local exclusive election-operation locks with bounded acquisition time, including the voting gate and nested operations. Keep the existing cache locks for other profiles. Keep lock files outside resettable election data and do not delete them while the application runs. Stop all writers when switching lock protocols.
3. Return a clear busy error only when the outer gate was not acquired. Preserve uncertain outcomes and do not automatically repeat election operations. Cover all affected Inertia and JSON actions.
4. Design and test durable recovery of finalization, VVPAT redemption, print submission, confirmation and deposit before moving slow work outside the gate. Preserve release and ballot identity. An unknown CUPS result requires operator reconciliation of queued and buffered copies before another print.
5. Order Reverb after MySQL and verify dependency outage and recovery without modifying election state.

## Verification

Run isolated tests of separate-process contention, long-running holders, terminated holders, nested lock failures, concurrent voting and closeout, partial writes, ambiguous printer submission, repeated confirmation, and recovery. Run the relevant workflow sequentially against isolated test storage. Physical printer and scanner checks require separately authorized operator action; automated checks do not establish paper output.

## Recovery Design

- Finalization is keyed by the original authorization. Reconciliation must identify the existing release and verify its ballot, serial, payload and authorization before completing any missing step. A conflicting or incomplete record blocks progress. A completed authorization with a lost response must be recoverable only by the same authorized session. Never create a second release to recover the first.
- Paper-ledger event files and their hash chain are evidence; the state and payload index are derived. A stale or conflicting state must block new issuance. Repair may rebuild derived records only after verifying the complete event chain and matching ballot identity; it must not overwrite events or invent missing evidence.
- VVPAT recovery must persist the release identity before redemption and record a print intent before invoking a printer. A process interruption or ambiguous submission leaves an unresolved attempt. Do not infer non-submission from a timeout, retry automatically, or confirm a deposit from a CUPS status. A trained operator must account for queued and buffered copies before an explicitly authorized new attempt.
- Confirmation must retain its pending record through deposit reconciliation. A repeated confirmation verifies the same release, ballot, serial, payload hash and sealed record; it completes only missing derived ledger and release state after integrity checks. Conflicts, invalid journals, and frozen or inconsistent ledgers block recovery and preserve existing evidence.
- Fault-injection tests must stop and restart at each persisted boundary, exercise the same recovery twice, and verify one release, serial, sealed record, device-ledger record and valid journal chain. Include mismatched identity, corrupted state and uncertain printer submission, with no automatic print or silent evidence repair.

## Rollout

Review and pin the revision; stage dependencies and assets, establish protected backups and rollback, and schedule maintenance. Stop all writers before changing the lock driver or code. Preserve application configuration, election data, storage ACLs, pending VVPAT state, printer queues, and scanner configuration. After deployment inspect services and natural heartbeats without synthetic voting, printing, scans, or queue replay.

## Current Status

The local implementation is in progress. Duplicate authorization releases, stale or damaged paper-ledger state, and VVPAT attempts with an uncertain or failed outcome fail closed locally. A pending VVPAT records its release identity before redemption, and recovery checks that identity against the control number. A role-demo workflow permits an officer to attest that no usable paper exists and that the identified job and printer buffer were checked before authorizing a separate reprint. It requires the single-host lock, checks the current attempt and journals the attestation; it does not print or deposit. The user selected demo-only use: this workflow is restricted to public-simulation storage in rehearsal or automated-test runs. The existing role-demo officer credentials are demo credentials and do not establish commissioned access control. Interrupted deposit confirmation retains the pending VVPAT in a fail-closed state, and unresolved VVPAT state blocks closeout. Short state writes and incomplete journal lines are detected rather than silently accepted. Full finalization and deposit reconciliation and the full fault-injection matrix remain unimplemented. The appliance has not been updated. Complete and verify recovery before representing the system as robust or deploying these changes.

Automatic reuse of an existing finalization remains disabled even when the visible evidence appears complete. Authorization completion, receipt printing, release redemption, run switching, and candidate-map updates do not yet share one protocol. Recovery must first bind reads to an immutable run and candidate-map snapshot, serialize all relevant writers, and distinguish a new release from a recovered response so receipt printing and analytics cannot repeat. Deposit recovery must verify sealed, paper-ledger, device-ledger, release and audit evidence together before completing or clearing pending state.

The receipt protocol must hold a non-expiring scope lock keyed by the stable base storage root across run validation, intent creation and printer invocation. It must not vary by run type or public-simulation round: those contexts can share run paths or replace the active scope. Every run-switch, reset, activation, demo-round change and relevant release writer must obey the same lock order, with the scope lock outermost. Before calling any printer, create an exclusive, per-release intent that contains no control number or QR and is durable across power loss, including file and parent-directory synchronization on the target filesystem. Any existing, partial or unreadable intent blocks automatic resubmission. A missing job file, a timeout or a failed command does not prove that CUPS or the printer received nothing. Explicit reprints need their own operator reconciliation and must not bypass an in-flight submission.

CUPS receipt submission errors are now recorded as uncertain, and the demo reprint action blocks jobs marked uncertain or failed. This is containment only: a process may stop before that status is persisted, and a generated file job is not a durable submission intent. A run-ID collision now blocks without replacing its directory, and a pointer to a missing or mismatched run directory blocks implicit creation. Election-day reset can still leave a stale legacy pointer; it now requires operator investigation instead of silently returning a deleted run. These checks do not serialize competing writers; test pointer changes, reset and collisions again as part of the shared-scope protocol before deployment.

The demo reconciliation request now requires an already-open round and precinct, verifies the officer before applying the scope, and refuses a missing run. It no longer creates or opens a precinct or changes lifecycle state merely to handle a reconciliation request. The round can still change concurrently until all relevant writers participate in the shared scope lock.

A local process-held base-root lock primitive now has isolated tests for exclusion across demo scopes, nested use, failure cleanup and termination. For the local profile, election HTTP requests acquire it before route binding or controller work and hold it through the response, outside the voting and narrower locks. This serializes participating HTTP requests, but CLI and any other writers have not all adopted the protocol, so it does not yet protect the run boundary against every writer. All entry points must acquire it in the same outermost order, and all deployment writers must use the same protocol before the lock can be relied on. Long-running browser-walkthrough commands invoke HTTP and cannot hold this exclusive lock across the child browser request.

The local-profile round reset, archive, scenario, field-rehearsal and facilitated-usability commands now hold the same base-root lock for their operation. Scanner listeners take it around each framed scan rather than while waiting for input. If they cannot acquire it before ingestion, they report that the scan was not recorded and instruct the operator to retain and rescan the document. These commands do not complete the writer audit: the other CLI paths, walkthrough lifecycle and any non-application writers still need coverage and process-level tests before cutover.

The observation-review, improvement-backlog, usability-session-kit, review-kit, retention-review, recovery-inspection, POP/CLC import, precinct package activation and candidate-report commands now acquire the base-root lock before looking up or writing election evidence. The guarded run and reporting commands restore the previous storage directory, run type, precinct, district and officer configuration after success or failure, including in long-lived processes. The browser walkthrough now takes the lock for setup and finalization, leaves it free while the browser runs, and revalidates the walkthrough and rehearsal pointer before finalization. Its active-run reservation still must be enforced by all competing run and round writers, and a real browser/competing-writer test is outstanding. Other entry points still need explicit treatment; a network transfer or browser callback must not simply hold the exclusive lock indefinitely.

The walkthrough control record now lives at the base storage root and is checked under the run lock by local-profile election HTTP requests, guarded commands and scanner ingestion. While it is active, those paths reject competing work; local callbacks carrying the matching token still undergo walkthrough authorization. An expired active record remains blocked rather than being cleared by those paths, and an unreadable reservation produces a fail-closed HTTP response. Legacy controls found under scoped demo directories also block work for operator investigation rather than being ignored. Control writes detect short writes, but remain non-atomic and are not guaranteed durable across power loss. An isolated separate-process test exercises a callback holding the run lock against a competing reset command. Other CLI entry points and direct service/filesystem writers can still bypass this reservation. The legacy-directory scan runs on each protected request and its impact needs measurement on the appliance.

The fresh review presentation service also acquires the base-root lock and checks the reservation before closing a room or creating a run, including when invoked directly. Tests cover an active walkthrough and a competing process holding the lock. Other direct service and filesystem writers still require an audit and protection.

Direct scenario execution and sample-package activation now take the same local-profile lock and refuse an active walkthrough before changing runs or packages; even an authorized walkthrough callback cannot start a competing scenario. Configured-precinct activation now takes the outer scope lock before its activation lock and accepts an active reservation only for a request verified by the outer HTTP middleware, with the same open rehearsal run, root and precinct. The verified request context is cleared after the request. It no longer performs its cached-activation read when the current run is absent or belongs to another precinct, avoiding implicit run creation during preflight. Public-simulation and demo-room walkthroughs use a different scoped storage root, which is not bound in the reservation; their commands now fail before creating a round in the local profile until that binding is designed and tested. Scenario execution can include cloud mirroring while an outer caller holds the lock; the upload boundary must be revised before relying on that combination.

The proposed scoped walkthrough binding must be created under the base-root lock from the server-selected round and precinct, before the browser starts. The reservation must identify the round and precinct database IDs and codes, clustered precinct, exact scoped storage root and its pre-existing rehearsal run ID and path, in addition to the base evidence run. Every scoped callback must verify the request-bound token, the current open base pointer, the selected round and precinct, and the scoped pointer and run context against that binding before applying the scope or writing. Missing, replaced, symlinked, or mismatched evidence must block without creating a run. Setup interruption must preserve any partially created run for investigation, and callback failure must restore request and configuration state. Completion and operator recovery must account for both runs: the current evidence archive only collects the active base run, so it must not represent itself as a complete archive of the scoped simulation. Re-enable these walkthrough modes only after a verified two-run evidence strategy, process-contention and interruption tests, and real browser coverage for both modes are in place. Reservation paths that are symbolic links now fail closed instead of being treated as an absent reservation.

District reconciliation now refuses output inside the configured election storage root, including resolved symlink aliases, and uses exclusive output creation with checked writes and ownership-aware cleanup. In the local profile its service also checks the walkthrough reservation under the base-root lock. This protects the configured root and cooperating application writers; it does not protect other storage roots, hostile filesystem changes during a write, or durability after power loss.

For a stopped rehearsal walkthrough, the local operator command `php artisan election:browser-walkthrough:recover <run-id> --coordinator-stopped` can explicitly recover the existing run without starting a replacement. The operator must verify that both the coordinator and its browser are stopped before providing the attestation. It holds the run lock, requires evidence that the coordinator PID no longer exists, validates the exact reservation and run ID, run pointer and any existing completion/report hashes and identities, and refuses symlinks, partial recovery records or pre-existing finalization files. Interrupted runs are finalized as failed for review even if a preserved completion record says it passed. A live or indeterminate coordinator, mismatched evidence, or an interrupted recovery requires investigation rather than automatic repair. PID checks and self-hashes do not provide authenticated process identity or evidence; uncoordinated writers and power-loss durability remain unresolved.

Evidence mirroring is now restricted to the local-lock profile and a locked rehearsal or automated-test run. It selects an existing run without creating one, makes a private local copy while holding the run lock, rejects links and inconsistent finalized indexes, and releases the lock before uploading. Each upload uses a new versioned destination; files and the manifest are read back and checked, and earlier versions are not deleted. Isolated tests cover competing publishers, lock contention, rejected evidence, partial upload and cleanup failure. Incomplete uploads can leave an unadvertised partial version; process termination can leave a private local staging copy for operator review. A failed local cleanup is reported for operator attention. These checks do not protect against uncoordinated writers or establish authenticated evidence, crash-durable local storage, remote retention, or an atomic latest-version pointer. The remaining writer audit and additional interrupted-copy and upload tests are still required.

Before a private-release deposit writes a sealed record, it now checks the full paper-ledger chain and matching issuance identity and index. Missing or inconsistent issuance blocks the deposit, and issuance verification also compares the event's payload hash. CUPS ballot submission errors are recorded as uncertain. These checks do not reconcile an interrupted deposit or guarantee that evidence remains unchanged between verification and later writes; the shared lock and cross-ledger recovery protocol remain necessary.

The demo reprint workflow also requires officer reconciliation when a prior attempt is awaiting confirmation. Direct reprint is blocked until the operator attests that no usable paper exists and the queue and buffer were checked; confirmation of a successfully printed VVPAT remains available. Unrecognized or inconsistent pending states fail closed. This does not establish physical printer state or replace the outstanding shared-scope and durable-intent work.

Each authorized demo reprint is now bound to the attesting browser session, current run, release, attempt and a fresh revision. The voting gate checks the binding before the printing state is written; stale, replayed or differently scoped requests cannot use a later authorization. A new review can replace a grant if the officer's session is lost. Session binding does not turn demo credentials into commissioned access control, and crash-durable intent plus separate-process race and fault-injection tests are still required.

The demo's latest control-number receipt lookup now blocks if valid jobs tie by modification time or any job is unreadable, malformed, incomplete or has an unexpected artifact path or status. It rechecks the selected job's contents under the voting gate. Before CUPS receipt submission, the job is marked `submitting`, which blocks a later demo reprint if the process stops before recording an outcome. These are containment measures: modification time remains mutable and does not prove chronology, and the marker is neither exclusive nor guaranteed durable across power loss. Replace the lookup with a verified explicit attempt reference and complete the durable intent and shared-scope protocol before relying on receipt recovery.

Authorization completion now uses the same authorization lock as claim and issuance. A lock timeout during finalization is surfaced as an uncertain outcome requiring operator attention; a focused test verifies that the existing release is preserved and no automatic control-number receipt is submitted on that request or a retry. This containment does not provide automatic finalization recovery or prove the outcome of a prior printer submission.

JSON state and generated artifact writes check for short writes and fail rather than reporting success. This check detects a failed write but does not make replacement atomic or guarantee persistence through power loss.

The deployment-readiness review identified expiring nested locks, a non-gated finalization path, and activity-journal concurrency and interrupted-append risks. The local profile now uses process-held election-operation locks, release creation has its own lock, and journal appends are locked and validate the existing chain. The paper-ledger and journal checks repeatedly scan their chains; measure their impact at expected scale. These changes do not make multi-file finalization or deposit atomic. The logging path must not change an operation's result if timing logs fail.

An isolated `field-50-ballots` test initially failed Friday certification because distinct test ballots with identical selections lacked distinct serials and collided as duplicate payloads. Certification now gives each test ballot a distinct test-only serial; targeted tests verify identical selections count separately while a repeated QR is rejected. The isolated scenario passed with its expected test precinct and the local lock profile in approximately 261 seconds. Development-Mac timings are not appliance benchmarks or comparisons against an unchanged baseline.
